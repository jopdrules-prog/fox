# FOX Camera Assist 1.1.0 — staged updates

The stable launcher is installed once under the existing per-user LocalAppData
FOX_Camera_Assist. It loads the current version slot. A fixed HTTPS channel under
jopdrules-prog/fox/fox-camera supplies a manifest and a versioned JSON ZIP package.
Only code is published; no user data, camera frames, passwords, prices or product photos.
Hashes validate both package transport and installed file bytes. Redirects are rejected.
This trust model uses the GitHub account plus HTTPS; hashes are not independent signatures.

Startup checks and applies ready releases. A background worker stages hourly and has
no apply/restart path. Version folders are immutable; current changes only after the
new subprocess responds with the expected health version. Failed starts terminate only
that child, restore backed-up config.json/remembered.json, block that release, and run
the previous slot. Dependency environments are keyed by requirements hash; a matching
legacy runtime is reused without modification. Previous versions and data backups are retained.
Runtime images, models and learned features stay local. Approval tokens and in-memory
OBS passwords never survive restart. The original FOX Center/helper code is untouched.

Validation: 43 tests pass including stage-without-activation, corrupt downloads,
traversal, offline pending activation, failed-start rollback/config restoration,
blocked versions, live-server noninterruption, locking, and prior camera/approval tests.
Initial installer migration and real server startup also receive isolated smoke tests.
Windows shell execution and the user's three devices require field confirmation.
Do not say the user's installation is enabled before they run the setup and new shortcut.

Maintenance: edit fox-camera/src, update VERSION and UI/health versions together,
run the tests, build package.json and latest.json with build_release.py (source directory
name adjusted to src in repo). Publish the immutable release first and advance latest.json
only after validation. Do not reuse a released version number or edit fox-center paths.

## 1.0.1 startup fix

Windows exclusive socket binding now disables the address-reuse flag inherited from HTTPServer before calling TCPServer.server_bind. The original implementation could combine SO_EXCLUSIVEADDRUSE and SO_REUSEADDR, which Winsock rejects. On failure the launcher prints the actual OS error rather than treating every OSError as an occupied port. Dependencies, runtime location and user data are unchanged.

19 tests passed after this fix: the existing 17 consent tests plus simulated Winsock exclusive-bind regression and actual local HTTP startup/occupied-port tests. The Windows regression uses the real TCPServer bind implementation with a socket test double that rejects conflicting options. An actual Windows machine was unavailable for validation; the user's next run must confirm startup there.

## Data flow

The main desktop companion reads the selected OBS camera input with authenticated OBS WebSocket 5 `GetSourceScreenshot`, retrieves registered product media through the helper's authenticated loopback HTTP API, and ranks local CLIP image embeddings. Camera sampling is every four seconds, after the user starts it. The quantized vision model uses ONNX Runtime CPU with two intra-op threads and one inter-op thread. The Windows process uses below-normal priority.

The companion uses the helper's normal local home-page session, keeps the session cookie private, and issues `/api/active` only from explicit approval and explicit undo handlers. OBS calls are allowlisted read-only calls. No scene transforms, stream controls, source URLs, or OBS input settings are changed. The existing helper display source follows the approved product through its existing polling.

## Consent state

- Sampling requires a manual start after preparation. Restarting does not resume sampling.
- Three consecutive samples with the same leading candidate and low pixel motion are needed.
- Confidence is a ranking heuristic, not a calibrated accuracy probability. No accuracy percentages are shown.
- One immutable proposal token binds candidate IDs, camera embedding/small image signature, helper selection/revision and configuration epoch.
- Proposals expire after 20 seconds. Image changes, manual product changes, disconnection and pause invalidate them.
- Approval requires an explicit `confirmed: true`, a still-current token, a candidate in the bound list, a fresh camera sample, and unchanged helper state.
- Tokens are consumed before the helper write. Failed/uncertain writes are not automatically retried.
- HTTP mutations require an authenticated session, same Origin/Host, and a custom header. LAN clients must pair with a rate-limited eight-digit code.
- OBS password stays in process memory and is excluded from state, disk, and request logs.

The helper's existing `/api/active` does not implement atomic compare-and-set. The companion checks the helper revision immediately before writing, but a separate manual controller can still race within the HTTP read/write interval. Avoid simultaneous approval and manual switching from another controller. A future coordinated helper release could add an expected-revision write without modifying this companion's consent rules.

## Matching limits

The matcher is CLIP visual similarity, not a clothing identity classifier. It has not been calibrated against the user's real camera and all physical garments. With editorial-only images it compares upper-body and lower-body crops. Registered original photos take priority. Manually remembered actual-camera embeddings can improve a garment's retrieval; six examples are retained per product+editorial filename. The user must still inspect the proposed image.

Uniform frames are ignored. Multiple garments, hands, similar black garments, moving cloth and the difference between real garments and generated editorials remain sources of error. Selection of a camera-only source and a tight region of interest is required. No claim of validated real-world garment accuracy is made.

Required packages are pinned in requirements.txt; model download is a separate explicit UI action. Closing the companion stops recognition, without stopping the helper or OBS.
